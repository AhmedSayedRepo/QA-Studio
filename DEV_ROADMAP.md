## What this app is
Flet **0.85.3** (pinned) desktop app — an Azure DevOps test-case / test-plan generator. Core files:

- `main.py` (~7,260 lines) — `class QAStudio`: all screens, shell/nav, window chrome, dialogs, self-update, login gate.
- `engine.py` (`E`) — providers/config (`E.AI_CONFIG`), generation, `apply_update`.
- `regression.py` — Regression + Test-Plan screens; `_checkbox_multiselect` (the custom inline dropdown used on Setup too).
- `sprint_titles.py`, `users_screen.py` — those screens.
- `theme.py` (`T`) — design tokens (`T.VIOLET`, `T.INK`, `T.R`, …) + `apply_theme`.
- `store.py` — DPAPI-encrypted creds (`store.load()` / `store.save(self.creds)`).
- `auth_supabase.py` (`auth`) — external auth gate + per-user permissions.
- `installer.py`, `install.bat`, `release.bat`, `_sync_to_install.py`.

### Toolchain / processes
- **Run (dev):** `C:\Users\proga\AppData\Local\Programs\Python\Python312\python.exe main.py` (GUI: `pythonw.exe`). This 3.12 has Flet; a co-installed 3.14 does NOT — desktop shortcuts must point at the 3.12 `pythonw`.

## Session changes (2026-07-09)
- **Automation — sequencing bug fixed (the real 'wrong sequencing' cause).** `validate_and_sequence_suite` (`engine.py`) sorted each story's cases with `key=lambda c: (c["bucket"], c["title"])` — the title was a SECONDARY sort key, so within a bucket cases were reordered ALPHABETICALLY by title text instead of keeping their authored order. That scrambles any intended step sequence (e.g. "create X" needs to run before "verify X exists"), and Arabic/English mixed titles sort by Unicode range, nowhere near logical order. Fixed to `key=lambda c: c["bucket"]` — Python's sort is stable, so cases now keep their original per-story order within each bucket. Applies to all three targets (Selenium/Playwright/Cypress) since they all consume the same `sequenced` output.
- **Automation — sequencing log, blank entries.** A case with no generated title used to log a blank line (silently skipped). Now logs `(untitled test case)` so every entry is identifiable.
- **Automation — Browse folder picker actually works now.** Root cause: `_browse_auto_folder` called its native-dialog attempts SYNCHRONOUSLY from the Flet `on_click` handler (Flet's own event-loop thread) — a blocking native dialog on that same thread silently failed every time (an earlier attempt at a zero-dependency ctypes/shell32 picker had the same problem and was reverted). Rewritten to mirror `regression._ask_save_path` exactly (the working exporters' 'Save As' dialog): a tkinter dialog run on a background thread via `threading.Thread`, tri-state return (`str` picked / `None` cancelled / `False` unavailable). Cancel now does nothing (no toast); the toast only fires when no native dialog is available at all.
- **Automation — README/.gitignore now always match the actual framework.** New `engine.sync_project_readme()` + `_detect_project_framework()`: on every `push_to_git()` call, detects the on-disk framework (`pom.xml`/`playwright.config.js`/`cypress.config.js`) and rewrites `README.md` + `.gitignore` from the correct template if they've drifted — covers a fresh generate-and-push AND pushing an old/forgotten-run folder via Browse that this session never regenerated. Also removed a second copy of the same bug: `push_to_git` had a hardcoded Maven-only `.gitignore` write that unconditionally overwrote whatever the sync had just written, on every push, for every framework (silently clobbering Playwright/Cypress `.gitignore`s).
- **Automation — Git push, friendlier rejection + Force-push retry.** A non-fast-forward push rejection used to dump git's raw multi-line hint text into the Activity log. `push_to_git` now returns one plain sentence (`"rejected: ..."`), and `_push_automation` (`main.py`) offers a confirm-dialog Force-push retry instead of leaving the user stuck.
- **Automation — auto-create the GitHub repo for a brand-new output folder.** New `engine._github_ensure_repo()` / `_parse_github_owner_repo()`: before pushing, if this folder has never been pushed before (no `git_pushed` marker in `.qastudio/manifest.json`), and the remote is `github.com`, check whether the repo exists and create it (private) if not, then push normally. Already-pushed folders skip the check. GitHub only — Azure DevOps/GitLab repo creation isn't wired up. Needs a PAT with repo-creation rights (classic `repo` scope, or fine-grained `Administration: Read and write`) — the PAT info icon (`main.py` HELP `"git_pat"`) and Help & guide → Automation were updated to explain this.
- **Automation — 'TODO' counter chip relabeled.** The Activity header chip literally read "TODO — locators resolved at runtime" (a leaked dev-facing label). Renamed to "Locators self-healed at runtime"; the counting logic is unchanged.
- **Auth — idle-logout dialog can no longer appear on the login screen.** `_show_idle_warning` and its countdown loop now bail/close quietly if the session isn't authenticated, instead of the countdown floating over the (unauthenticated) sign-in gate mid-session-end race.
- **Email reports — accent color now matches the app instead of an unrelated blue.** Both `build_report_email` (test-case generation run report) and `build_sprint_summary_email` had their own local `VIOLET="#3A57D6"` (a royal-blue, plus a deeper-blue `VIOLET_INK` and pale-blue `VIOLET_SOFT`) hardcoded just for email HTML — completely unrelated to the app's actual accent color (theme.py's `VIOLET`/`VIOLET_INK`/`VIOLET_SOFT`, which despite the name is a cyan/teal tone: `#0E9CC0`/`#0B6E86`/`#D6F4FB`). Both now use the app's real values, so the "Completed" status accent, headline count, CTA button, per-story section dot, and log "story"/"info" line colors in the emailed report all match the in-app color tone.
- **Run — added Copy log / Clear log, matching Automation.** The Run screen's RECENT ACTIVITY panel now has the same pinned Copy/Clear icon-button toolbar as Automation's Activity log (same visual "chip" style, Clear red-tinted). Refactored the clipboard-copy logic into one shared `_copy_log_text()` (Run and Automation both call it, so they can't drift out of sync) and added `_copy_run_log`/`_clear_run_log`. Clear is a scoped update to `_log_col` (no full `render()`), and correctly resets `_rendered_count` to 0 so a line logged right after Clear still renders (the Run screen's log uses an incremental "append only what's new since last render" optimization keyed off that counter — leaving it stale after a clear would have silently swallowed the next line or more until the log grew past the old count again).
- **Automation — Copy log's OS-clipboard fallback no longer hangs the next paste.** The tkinter-based fallback added for Copy log (`clipboard_clear()`/`clipboard_append()`) had a real, reproduced bug: Windows' clipboard normally uses delay-render — the text isn't actually handed to the OS at append time, the calling window just registers itself as able to produce it LATER, when something else pastes. That code destroyed the hidden Tk window immediately after, so the next paste (e.g. into Notepad) hung waiting for a response from an already-dead window. Replaced with `_win_clipboard_set()`, a direct ctypes `OpenClipboard`/`GlobalAlloc`/`SetClipboardData`/`CloseClipboard` write (same explicit-argtypes rigor as store.py's DPAPI code, to avoid 64-bit pointer truncation) — the text is committed to the system clipboard synchronously inside the call and ownership of the memory transfers to Windows itself, so there's nothing left alive for a later paste to wait on. Verified with a mocked-Windows-API test confirming the exact call sequence, correct UTF-16LE + NUL-terminator encoding, and that `CloseClipboard` still runs even if a later step fails.
- **Automation — Clear log is now a scoped update, not a full-screen render.** Matches the same reasoning as the push-flow fix: `_clear_auto_log` called `self.render()`, rebuilding the entire Automation screen (left-hand form included) just to empty the log. Now swaps `_auto_log_col`'s own content back to the empty-state placeholder in place, falling back to a full render only if the log column doesn't exist yet.
- **Setup — Azure Organization is now genuinely isolated per account.** `self.creds["org"]` was always stored per-account correctly, but three places fell back to the shared `E.AZURE_ORG` engine-global when the CURRENT account had none saved: the Setup screen's displayed field value, `_connect()`'s org resolution, and `_switch_user_creds()` never reset that global at all on an account switch. `E.AZURE_ORG` isn't itself per-account (it's a plain module global used for every live Azure DevOps API call) and starts out holding a hardcoded dev-default org — so a second account signing in on the same running app could see a PREVIOUS account's organization pre-filled in their own Setup field, silently save it into their own creds if they clicked Save/Connect without noticing, or even have live API calls run against the wrong org invisibly (field could look right while `E.AZURE_ORG` itself was still stale). Fixed: `_switch_user_creds()` now resets `E.AZURE_ORG` to this account's own saved value (or blank) on every switch; the Setup field and `_connect()` no longer fall back to `E.AZURE_ORG` — a genuinely unset org is now a required-field error on Connect, same as the PAT/API key, instead of a silent cross-account fallback. Verified with a scripted two-account test (Account A connects, Account B switches in — engine global and field both correctly go blank, Connect is blocked until B enters their own org).
- **Automation — fields (PAT, Git URL/branch, site/login URLs, project folder) now actually persist across restart/re-login.** Real root cause of "I pasted a new PAT and it wasn't there next time": `self.auto_git_token`/`auto_git_url`/`auto_git_branch`/`auto_site_url`/`auto_login_url`/`auto_login_user`/`auto_login_pass`/`auto_local_path` were only ever seeded ONCE, in `__init__` — which runs and reads `self.creds` **before** `store.set_user(uid)` ever points at the signed-in account's own per-user file (that switch happens later, asynchronously, once silent session-restore resolves who's signed in). So these fields were seeded from the SHARED DEFAULT file, not the account's own. The save itself was never broken — pasting a PAT correctly wrote it to the right per-user file once already signed in — but on the *next* launch `__init__` read the default file again before the real per-user file was ever loaded, so the field looked empty/reverted even though the save had succeeded. `_switch_user_creds()` (main.py) now re-syncs these 8 fields from the freshly-loaded per-user creds, the same way it already did for theme/lang/tool — applied unconditionally, since this only runs at sign-in / startup session-restore / sign-out, never while a field is actively being edited. Verified with a scripted test reproducing the exact before/after.
- **Auth — dark/light picked on the login screen no longer gets discarded on sign-in.** Real bug (found after the sign-out fix above still left the reverse direction broken): `login.py`'s sign-in handler used to apply + save `app._login_theme` (the login screen's own choice) to `app.creds` and call `store.save(app.creds)` **before** calling `app._switch_user_creds()`. But that save happened while the pre-sign-in (shared/default, `uid=None`) creds file was still active — `_switch_user_creds()` immediately after then loaded the signed-in account's own per-user file and, per its own theme-sync logic, overwrote `T.MODE`/`page.theme_mode` with **that** file's saved theme. Net effect: picking dark on the login screen and signing in landed you back in whatever theme that account last had saved (often light), silently. Fixed by reordering — `_switch_user_creds()` now runs first (loading the correct per-user file), and the login screen's chosen theme is applied and persisted into `self.creds` *after*, so it's the one that sticks.
- **Auth — login screen now matches the app's theme after sign-out.** Root cause (pre-existing, not introduced by the guard above): `login.py`'s login gate keeps its own independent theme flag, `app._login_theme` — it's only ever set by the login screen's own toggle or copied INTO `creds["theme"]` on a successful sign-in; nothing ever synced it back FROM the app's theme on the way *out*. So the first time an app instance returned to the login gate after a sign-out, `_login_theme` was still unset and fell back to its hardcoded dark default — a visible flip to dark even if the app/account that just signed out was in light mode. `_sign_out()` (`main.py`) now sets `self._login_theme = T.MODE` right after `_switch_user_creds()` re-applies the now-active creds file's theme, so the login screen opens in whatever theme was just on screen. First-launch behavior (login defaults to dark before anyone has ever signed in) is unchanged.
- **Investigated, NOT changed:** the Automation Activity log's Arabic-text line spacing was tweaked (1px → 4px padding) earlier this session as a guess, then rolled back to the original 1px on request — no reproducible evidence the padding was ever the actual cause (Flet's `Text` control has no `rtl`/direction property to fix bidirectional layout with either, confirmed against the current Flet docs). What looked like "overlapping text" in the case that prompted this was actually the sequencing bug above, not a rendering issue — leaving log-line padding as-is unless a concrete repro shows otherwise.
- **Automation — Git push no longer resets the Activity log scroll.** `_push_automation` used a full `self.render()` at push-start, on Force-push retry, and in `finally` — each rebuilding the whole screen (including a brand-new log Column), snapping scroll back to the bottom 2-3 times per push. The Generate/Push buttons and the ACTIVITY spinner are now persistent `ft.Container`s (`app._auto_buttons_ctr`, `app._auto_spinner_ctr`) refreshed in place via `automation._refresh_auto_state(app)`; the log column itself is never touched by a push, so scroll position holds.
- **Automation — Activity log entries no longer render out of order.** Root cause: `_auto_logmsg`'s UI update went through `ui_safe()`, which (via Flet's `page.run_thread`) starts a **brand-new thread per call** with no ordering guarantee — so under fast logging (e.g. sequencing 32 cases back-to-back) the on-screen `Column` could show "Sequencing case 1/32" before the "Sequencing N test case(s)…" header, or a case's title several lines away from its own "Sequencing case k/N" line, even though the underlying `self._auto_log` list was always correctly ordered. Fixed by (1) a `self._auto_log_ui_lock` serializing the column catch-up so concurrent `upd()` calls can't race on `len(col.controls)`, and (2) each `upd()` now appends every entry in `self._auto_log[have:real]` (read fresh from the authoritative list by index) instead of only its own closure-captured message — so whichever thread happens to run, first or last, always paints the full correct sequence. Verified with a scripted race test (multiple `upd()`s started in scrambled order, several runs) confirming on-screen order matches the log list every time.
- **Automation — Copy log actually copies now (and fails loudly, not silently, if it truly can't).** `_copy_auto_log` was reported failing with "Couldn't copy the log." every time on a long-running automation's log (dozens of `Sequencing case k/32` + Arabic-title lines, several thousand characters). Two bugs, both fixed: (1) the failure toast was rendered via `_toast` (always green/success-styled, per its own hardcoded `T.GREEN` + checkmark icon) instead of `_err` (red) — so a genuine failure LOOKED like a success in the screenshot that surfaced this. (2) The only clipboard path was `page.set_clipboard()`, which goes over Flet's own IPC channel to the Flutter client and may have an undocumented payload-size limit on a long log; there's now a fallback that sets the OS clipboard directly via `tkinter` (the same native layer already proven reliable for the Browse-folder picker) if `set_clipboard` raises, and only shows the red error toast if BOTH paths fail — and via a new `_clip_fail_reason()` classifier, that toast is now one plain-English sentence ("clipboard support isn't installed…", "no display is available…", "the app window didn't respond in time…", "another app has the clipboard locked…") instead of a raw exception dump, falling back to the exception's own (truncated) text only when nothing more specific matches.
- **Automation — Copy log / Clear log.** Added two icon buttons to the ACTIVITY header: copy the entire log to the clipboard (skips blank lines, toasts if there's nothing to copy), and clear it (`self._auto_log = []` + re-render). Later moved into a pinned toolbar row at the very top of the log rail itself (a fixed sibling of the scrollable log `Column`, inside the same bordered box, separated by a divider) so it stays put while the log scrolls beneath it, and redesigned as rounded icon "chips" — Clear is red-tinted to read as destructive, Copy stays neutral.
- **Automation — Stop no longer waits out the current AI call.** `validate_and_sequence_suite`'s per-case `compile_test_case(...)` call is a blocking HTTP request (up to a 90s timeout) that was invoked directly, so clicking Stop mid-case only took effect on the *next* case — up to 90s of apparent hang. Wrapped it in `_run_stopaware` (already used by the Run screen's Titles/Steps generation): a background thread runs the call while the main loop polls `should_stop()`/the global stop event every 0.3s and raises `StopRequested` the instant Stop is clicked, abandoning the in-flight request (harmless — it finishes on its own timeout with no side effects). Verified with a scripted test: Stop clicked ~0.3s into a simulated 5s blocking call aborted in ~0.3s, not 5s.
- **Setup — Email sender config is Admin-only.** The Gmail sender address/name + App Password fields are hidden from non-admin users in both the edit and saved views (`_connection_edit`/`_connection_saved`) — they're a shared, org-wide credential used to send reports for everyone, not a personal setting.
- **Setup — Email config now syncs org-wide via Supabase (configure once, applies to everyone).** New Supabase table `public.org_settings` (RLS: any authenticated user may SELECT, no direct write policy) + a new Edge Function `org-settings` (mirrors `admin-users`'s pattern: verifies the caller's JWT, GET is open to any signed-in user, POST upsert requires `app_metadata.role === "Admin"`, service-role key stays server-side). Client side (`auth_supabase.py`): `get_org_settings()` / `admin_set_org_email(sender, sender_name, app_password)`. `main.py`: saving the sender address, sender name, or Gmail App Password (`_save_sender`/`_save_sender_name`/`_save_gmail`) now also calls `_push_org_email()`, which — only if the caller is a signed-in Admin — pushes the trio to `org_settings` in the background; every sign-in/session-restore/sign-out (`_switch_user_creds`) calls `_refresh_org_settings()`, which pulls the shared value in the background and applies it via `E.set_credentials(...)`. Fully best-effort and non-blocking: auth not configured, not signed in, offline, function not deployed, or a non-Admin caller all fail silently or with a distinct non-blocking toast ("Saved locally, but couldn't share with other users: …") — the user's own local save (`store.save`) always succeeds regardless, so email sending is never blocked by the sync layer. Backend already deployed (no manual setup step needed, unlike `admin-users`).
- **Email reports — unified design across all three report types.** The run report, Sprint Summary, and Regression/Sprint Plan emails used three different palettes and layouts, including a leftover royal-blue/purple gradient (`#3A57D6`/`#6A33A8`) unrelated to the app's real cyan accent. All three now share one palette (theme.py's cyan `VIOLET`/`VIOLET_INK`/`VIOLET_SOFT` family) and the same masthead + hero-pill + metric-strip + section-head + footer chrome — `_plan_html` (regression.py) was rebuilt to match `build_report_email`'s design language; `build_sprint_summary_email` was already aligned. - **Never** copy/modify large files (`main.py`, `regression.py`, `engine.py`) via shell `cp`/`sed -i` on mounted folders — it can silently truncate. Use the Read/Edit/Write tools (host) or `_sync_to_install.py`.
